Project Overview

This project focuses on building a reliable event-driven workflow connecting TradingView, Webhook communication, and external execution APIs.

The primary objective is to design a maintainable automation architecture capable of transmitting signals, validating requests, synchronizing system states, and handling failures gracefully.

Instead of emphasizing trading performance, this project demonstrates practical experience in API integration, system architecture, debugging methodology, and cross-platform communication.

Problem Solving

Engineering Challenges

Click each challenge to expand the full engineering context.

CHALLENGE 01

Position Synchronization

+
State Management

The Webhook handler and the Exchange API maintained separate state models. When a network hiccup delayed a response, the local state diverged from the exchange's actual position — causing the next signal to act on incorrect assumptions.

Solution: Introduced a reconciliation step before every order submission — always fetch the current position from the exchange API rather than relying on cached local state. This eliminated the drift problem entirely and made the system stateless from the handler's perspective.

CHALLENGE 02

Duplicate Alert Firing

+
Idempotency

TradingView occasionally fires the same alert condition twice in rapid succession — once when the bar closes and again on the next bar open. Without a deduplication layer, this resulted in double order submissions.

Solution: Implemented a time-windowed idempotency key on the Webhook handler. Each incoming payload is hashed; if an identical hash arrives within a configurable cool-down window, the request is acknowledged but silently dropped before reaching the API layer.

CHALLENGE 03

Partial Take-Profit Logic

+
Business Logic

Pine Script signals a take-profit as a discrete event, but the exchange requires a size-based order. Mapping a percentage-based exit to an exact quantity while accounting for already-filled partial orders required careful state tracking across multiple API calls.

Solution: Fetched the current open position size at execution time, computed the target quantity dynamically, and added floor/ceiling guards to prevent over-selling due to floating-point rounding in the exchange's API response.

CHALLENGE 04

State Management

+
Consistency

Across asynchronous events spanning three independent systems, keeping a single consistent view of state was the hardest problem. A dropped order or a delayed confirmation could leave the handler's model out of sync with the broker's reality — and the error was often invisible at the point of failure.

Solution: Made the handler stateless by always reconciling against the live broker position, and instrumented every boundary with structured logs — timestamp, payload hash, origin, and outcome — so any state divergence became immediately traceable across systems.

Looking Back

Reflection

The greatest takeaway was never a trading strategy. It was gradually coming to understand — through one debugging session after another — why system integration, API communication, event-driven architecture, and cross-platform collaboration matter so much.

Every bug forced me to re-examine my own design assumptions. Over time, that built a habit: analyze the problem first, verify the hypothesis next, and only then correct the workflow.

Through this project I didn't just finish an automation pipeline — I built an engineering mindset for facing unknown problems with continuous analysis, debugging, and optimization.
