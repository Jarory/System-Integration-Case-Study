發現問題

TradingView 能產生交易訊號，但實際下單平台彼此獨立，兩者無法直接溝通，只能依靠人工操作，不僅效率低，也容易發生錯誤。

發想

我開始思考，是否能建立一套流程，讓兩個原本互不相通的系統，自動交換資料並完成整個交易流程?

研究

為了完成整合，我研究了 TradingView Alert 格式、Capital.com API、Webhook 通訊方式以及 Make 的流程控制，釐清每個系統的資料格式與限制。

解決方案

最終採用事件驅動（Event-Driven）架構，以 Make 作為流程中介，負責驗證資料、串接 API、控制流程順序，提升整體可靠性與維護性。

最終成果

建立一套完整且可持續維護的自動化交易流程，從 TradingView 產生交易訊號，經由 Make 負責流程控制、資料處理與訂單狀態管理，最後串接 Capital.com API 完成下單，全流程皆可自動執行，並累積了跨平台系統整合、API 串接與事件驅動架構的實務經驗。

專案說明

本專案採用事件驅動（Event-Driven）架構，整合 TradingView、Webhook、Make 與 Capital.com API，建構一套具備流程控制、資料驗證、狀態同步及 錯誤處理能力的跨平台自動化交易流程，確保各平台間能穩定協作，並提升系統可靠性與可維護性。

本作品主要展示系統架構設計、跨平台整合、API 串接與除錯歷程，交易策略本身並非本專案重點。

工程問題

技術挑戰

點擊各項挑戰，可查看問題分析、解決方式與改善成果

案例 01

持倉同步

+
狀態管理（State Management）
問題
下一筆交易訊號有時會依據舊的持倉資料執行，導致部位重複建立或方向錯誤
根本原因
Webhook 與券商端各自維護持倉狀態，當 API 回傳延遲時，本地端資料可能與實際持倉不同步
解決方案
每次送單前重新向券商查詢最新持倉資料，再依據即時資訊計算下單內容，使流程不再依賴本地快取狀態
學習與收穫
跨系統整合時，不應完全依賴本地資料，應以實際來源（Source of Truth）作為判斷依據
案例 02

重複訊號觸發

+
冪等控制（Idempotency）
問題
同一筆交易訊號偶爾會被系統重複執行，造成重複下單
根本原因
TradingView 在特定情況下可能於 K 棒收盤及下一根 K 棒開始時再次送出相同訊號
解決方案
替每筆請求建立唯一識別值（Hash），並加入短時間內的重複檢查機制，相同訊號直接忽略，不再送往 API
學習與收穫
事件驅動架構應預設訊號可能重送，所有接收端都需要具備冪等（Idempotent）設計
案例 03

分批停利邏輯

+
商業邏輯（Business Logic）
問題
分批停利偶爾因數量不符合券商規範而被拒單
根本原因
百分比計算後的數量可能出現浮點誤差，導致送出的委託數量不符合交易所規則
解決方案
送單前重新取得最新持倉數量，動態計算實際可交易口數，並加入上下限與四捨五入保護機制
學習與收穫
所有交易數量都應依照 API 規格重新驗證，而不是直接相信程式計算結果
案例 04

系統狀態同步

+
一致性（Consistency）
問題
當系統發生錯誤時，不容易快速定位是哪個環節出了問題
根本原因
整個流程橫跨 TradingView、Make 與 Capital.com 三個平台，任何一個節點延遲或失敗，都可能造成資料不同步
解決方案
建立完整的流程紀錄（Log），記錄每一步的時間、來源、請求內容與執行結果，並搭配持倉同步機制，方便快速追蹤問題
學習與收穫
可觀測性（Observability）應在系統設計初期就納入考量，而不是等到發生問題後才補上

專案心得

這個專案最大的收穫，不是完成一套交易系統，而是在一次次除錯與驗證的過程中，慢慢理解系統整合、API 溝通、事件驅動架構，以及跨平台協作的重要性。

開發過程中，我遇到不少看似相同、實際原因卻完全不同的問題，這也讓我慢慢養成先分析問題、確認原因，慢慢修改程式的習慣，而不是急著嘗試各種修正方式，亂修會出事.....很多時候，真正需要修正的不是程式碼，而是對系統運作流程的理解。

面對問題、拆解問題、驗證問題，並理解出一套屬於自己的知識來解決問題，是我希望帶進每一個開發團隊的工程習慣！
